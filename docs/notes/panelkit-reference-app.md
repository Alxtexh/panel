# PanelKit Reference Application

A dummy clone of the production ISP billing system, built on PanelKit, used as the benchmark
harness and the proving ground for the kit.

> **NB — This is not a rewrite of production.** It is a throwaway replica with fake data, built on
> a desktop machine, whose only purposes are (1) to prove the kit can express every real surface,
> and (2) to measure speed portal-by-portal against the current system. It never connects to a
> production host, database, or credential.
>
> Read alongside `PANEL_KIT_BUILD_SPEC.md` and `PANEL_KIT_ADDENDUM_01.md`. Where they conflict,
> they win; this document only describes *what to build*, not *how*.

## 1. Purpose and ground rules

**What this proves:**

- The kit can express every surface shape in a real ISP billing SaaS.
- Three panels with different guards, paths, and tenant contexts coexist.
- Speed holds at realistic data volume, not demo volume.
- Switching between portals is fast, including as the same human with different roles.

**Ground rules:**

1. Fake data only, generated by seeders. No production dump, ever.
2. Local database, local Redis, local everything. `DB_HOST=127.0.0.1`.
3. Business logic is stubbed. A "suspend client" action flips a column and logs; it does not talk
   to RADIUS or a router. The point is the panel, not the ISP logic.
4. Every page must be reachable and measurable. A page that cannot be benchmarked does not count
   as built.
5. Visual polish is secondary to shape and speed. Do not spend time on branding here.

## 2. Stancl tenancy setup

The dummy must exercise Stancl properly, not fake it, because tenancy overhead is part of what is
being measured.

### Install and configure

```bash
composer require stancl/tenancy
php artisan tenancy:install
```

### Tenant model and domains

```php
// Tenant identified by domain, matching production behaviour
// central domain:  panelkit.test
// tenant domains:  acme.panelkit.test, zenith.panelkit.test, ...
// custom domain:   fake-isp.test   (one tenant, to prove custom-domain resolution)
```

Add all domains to `/etc/hosts` (or use `*.test` via Herd/dnsmasq):

```
127.0.0.1 panelkit.test acme.panelkit.test zenith.panelkit.test orbit.panelkit.test
127.0.0.1 nova.panelkit.test atlas.panelkit.test fake-isp.test
```

### Bootstrappers

Enable in `config/tenancy.php`:

| Bootstrapper | Enabled | Why |
|---|---|---|
| `DatabaseTenancyBootstrapper` | Yes | Needed for the one dedicated-database tenant |
| `CacheTenancyBootstrapper` | **Test both ways** | Run the benchmark with it on and off. The kit must be correct and fast in both, per Addendum Part A |
| `FilesystemTenancyBootstrapper` | Yes | Proves upload paths resolve per tenant |
| `QueueTenancyBootstrapper` | Yes | But jobs must still pass `tenant_id` explicitly |
| `RedisTenancyBootstrapper` | No | Off by default, matching the common production choice |

### Hybrid database mode, mandatory

This is the trap most likely to ship undetected, so the dummy must contain both modes.

| Tenant | Mode | Purpose |
|---|---|---|
| `acme`, `zenith`, `orbit`, `nova` | **Shared** central database with `tenant_id` column | The common path |
| `atlas` | **Dedicated** database, no `tenant_id` column | Proves the kit never writes `->where('tenant_id')` itself |

If a resource works on `acme` but throws on `atlas`, the kit has hardcoded a tenant filter. That
is the whole point of including `atlas`.

### Middleware per panel

```php
// Tenant admin + client portal: tenant context
['web', InitializeTenancyByDomain::class, PreventAccessFromCentralDomains::class]

// Super admin: central context, never tenant-scoped
['web']   // on panelkit.test only
```

## 3. Seed data and scale profiles

Five tenants of deliberately different sizes, mirroring a real SaaS distribution where most
tenants are small and one is large.

| Tenant | Domain | Clients | Sessions | Invoices | Transactions | Routers | Plans | Mode |
|---|---|---|---|---|---|---|---|---|
| `acme` | acme.panelkit.test | 250,000 | 2,000,000 | 900,000 | 1,200,000 | 60 | 40 | Shared |
| `zenith` | zenith.panelkit.test | 25,000 | 200,000 | 90,000 | 120,000 | 20 | 25 | Shared |
| `orbit` | orbit.panelkit.test | 2,500 | 20,000 | 9,000 | 12,000 | 8 | 15 | Shared |
| `nova` | nova.panelkit.test + fake-isp.test | 200 | 1,500 | 700 | 900 | 2 | 6 | Shared, custom domain |
| `atlas` | atlas.panelkit.test | 25,000 | 200,000 | 90,000 | 120,000 | 15 | 20 | **Dedicated DB** |

Rules:

- Seed with chunked bulk `insert()`, 5,000 rows per chunk. Model factories in a loop will take
  hours and you will stop running the seeder.
- Realistic distributions: roughly 70% active, 15% expired, 8% suspended, 5% trial. Do not seed
  uniform data, because uniform data hides index problems.
- Timestamps spread over 24 months so date-range filters and charts have something to do.
- `php artisan panel:seed-demo --tenant=acme --scale=xlarge`, resumable, reporting progress.

## 8. Dashboard versus workspace: the pattern

The production system uses two composition patterns, and the kit must support both natively.

### Dashboard: modular, conditional composition

The main dashboard assembles widgets **conditionally by enabled module**. Fibre widgets appear
only if the OLT module is on, rewards widgets only if loyalty is on, expense widgets only if that
module is on. Composition varies per tenant.

```php
Dashboard::make()
    ->widgets([
        AlertsWidget::class,                                   // always
        KpiWidget::class,                                      // always
        SubscriberTrendWidget::class,
        ...Module::when('fiber',   [FiberKpi::class, OnuStatusDonut::class, SignalHealth::class]),
        ...Module::when('rewards', [RewardsKpi::class, RunningNowTable::class]),
        ...Module::when('expenses',[ExpenseKpi::class, ExpenseTrend::class, CategoryDonut::class]),
    ]);
```

Requirements this places on the kit:

- Widget lists resolve per tenant, from feature flags, without a query per widget.
- Each widget is a **separate deferred prop**, so a slow one never blocks the others.
- Widget composition is part of the page payload, not the cached resource schema, because it
  varies per tenant.

### Workspace: a domain hub on one page

A workspace is a single page combining KPI widgets, one or more tables, and domain actions, for a
subject area that does not fit a plain CRUD resource. Production examples: Rewards, Expenses,
Equipment, SmartOltDashboard, Communications.

```php
Workspace::make('rewards')
    ->widgets([RewardsKpi::class, RedemptionTrend::class])
    ->tables([
        Panel\Tables\ActiveRewards::class,
        Panel\Tables\RedemptionHistory::class,
    ])
    ->actions([CreateReward::class, ExportRedemptions::class]);
```

Requirements this places on the kit:

- A page can host **multiple independent tables**, each with its own filter, sort, and pagination
  state, all reflected in the URL without colliding. Namespace the query parameters per table.
- Widgets and tables on a workspace load independently. One slow table does not block the others.
- A workspace is a first-class generated artefact: `php artisan make:panel-workspace Rewards`.

**The kit must ship both.** A framework that only does CRUD resources cannot express half of this
system.

## 10. Benchmark methodology

### What to record per surface

| Metric | How |
|---|---|
| Server time | Middleware timer, logged per request |
| Query count | Query log listener |
| Payload size | Response bytes, compressed and uncompressed |
| Client render | `performance.mark` around mount and patch |
| Time to interactive | Lighthouse or Playwright trace |
| Navigation time | Click to content painted, measured in the browser |

### How to run it

1. **Always warm up.** Three runs, report the median. A single cold run measures opcache, not the
   application. This produced false findings on the current system more than once.
2. **Per tenant scale.** Run the same suite against `nova` (200 clients) and `acme` (250,000). A
   metric that changes with row count reveals a missing index or an unbounded count.
3. **Both cache bootstrapper settings.** On and off, per Section 2.
4. **Both database modes.** `acme` (shared) and `atlas` (dedicated).
5. **Throttled network profile** for the client portal, simulating mobile data.
6. **Cross-portal journey**, timed end to end: tenant admin Clients list, switch to super admin
   Tenants list, switch back, open client portal as a subscriber. This is what you asked to
   measure, and it is the one number that captures whether the whole system feels fast.

### Ship it as a command

`php artisan panel:benchmark --tenant=acme --runs=3 --json` outputs a machine-readable report so
runs are comparable over time and can gate a build.

## 11. Comparison targets

Measured figures from the current Filament system, to beat:

| Surface | Current | Target | Multiple |
|---|---|---|---|
| Dashboard, first hit cold | ~840 ms | < 400 ms shell, widgets stream after | 2x+ |
| Heavy tabbed settings form | 500 to 710 ms | < 150 ms | 4x+ |
| Router onboarding wizard | ~967 ms | < 200 ms | 5x+ |
| Fastest pages today | 42 to 90 ms | < 50 ms | Parity or better |
| Any navigation | Full server render every time | < 150 ms, prefetched to near zero | 5x+ |
| Filter or sort change | Full component round trip | < 300 ms server, < 50 ms client | 3x+ |

Two extra measurements the current system cannot produce at all, so record them as new baselines:

- **Back-navigation:** must be instant from client cache, hitting no server.
- **Second visit to a page in the same session:** must not re-fetch the schema.

### Acceptance

- [ ] All five tenants resolve by domain, and `nova` also resolves by custom domain
- [ ] Every benchmark surface works identically on `acme` (shared) and `atlas` (dedicated)
- [ ] A resource never queries `tenant_id` directly; `atlas` proves it
- [ ] The benchmark suite runs warm, three times, and reports medians
- [ ] Every Section 11 target is met or the gap is documented with a reason
- [ ] The cross-portal journey is measured and recorded
- [ ] A workspace page hosts three independent tables with non-colliding URL state
- [ ] The dashboard composes conditionally per tenant module flags, with no query per widget
- [ ] No production host, credential, or data appears anywhere in the repository
