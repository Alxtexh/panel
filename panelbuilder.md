# PanelKit Build Specification

A complete, self-contained build spec for a reusable, SaaS-ready admin panel framework in the
spirit of FilamentPHP, but SPA-fast and with a fraction of the runtime overhead.

**Hand this document to a coding agent as-is.** It assumes no other context.

> **Rename before you start.** This spec uses the placeholder name `PanelKit`, the Composer
> package `panelkit/panel`, and the npm package `@panelkit/panel`. Replace all three with your own
> naming everywhere before generating code.

## 1. Mission and non-goals

### Mission

Build a package pair that lets a developer add a fully working, tenant-scoped admin screen to a
Laravel application by writing **one PHP class** and running **one Artisan command**, exactly as
FilamentPHP does, while the resulting UI behaves as a single-page application with no server
re-render on interaction.

Success looks like this:

```bash
php artisan make:panel-resource Client
# edit one file
# a working list, filter, search, sort, view, create, edit, and delete screen now exists
```

### Why not just use Filament

Filament re-renders components on the server for every interaction through Livewire. That
round trip is the latency floor. PanelKit sends a **schema once** and **data only** afterwards,
so interaction cost collapses to a JSON request and a client-side render.

### Non-goals

- Not a general-purpose replacement for Filament. It serves SaaS admin CRUD patterns only.
- Not a headless API. Auth stays session-based through Inertia, so authorization stays server-side.
- No support for anything other than Laravel 12+, PHP 8.4+, PostgreSQL, Vue 3, Tailwind 4.

## 2. Environment rules (read first)

**This is built entirely on a local desktop machine. There is a live production system that must
never be touched.**

Hard rules for the agent:

1. Never SSH to, deploy to, or reference any remote server.
2. Never point `.env` at a remote database. `DB_HOST` must be `127.0.0.1` or a local container.
3. Never copy a production `.env`.
4. Never run destructive commands against anything but the local database.
5. All test data is generated by factories and seeders. No production dumps.

### Local stack

| Component | Requirement |
|---|---|
| PHP | 8.4+ |
| Laravel | 12+ |
| Node | 20+ |
| Database | PostgreSQL 15+, local only |
| Runner | Laravel Herd, or Sail/Docker, or `php artisan serve` |
| Package manager | Composer 2, npm |

### Seed data at realistic scale

Performance claims are meaningless against 50 rows. The playground app must seed:

- 500,000 `clients` rows across 5 tenants
- 2,000,000 `sessions` rows
- 200 `plans`, 50 `routers`

Use bulk `insert()` in chunks of 5,000, not model factories in a loop, or seeding will take hours.
Provide `php artisan panel:seed-demo --scale=large|medium|small`.

## 3. Architecture

### The core idea

```
PHP Resource class
      |
      | toSchema()  -> cached JSON, sent once
      v
  Schema JSON  ------------------->  Generic Vue renderer
      ^                                      |
      |                                      | user filters / sorts / paginates
      |                                      v
  Data payload <-------------------  Inertia partial reload (data only, no schema)
```

Three separate concerns, never mixed:

| Concern | Lives in | Travels | Frequency |
|---|---|---|---|
| **Schema** (what columns, filters, actions exist) | PHP resource class | Once per resource per session, cached | Rare |
| **Data** (the actual rows) | Eloquent query | Every filter, sort, page change | Often |
| **Rendering** | One generic Vue page component | Never travels, it is in the bundle | Never |

Filament sends all three on every interaction. PanelKit sends only the middle one. That single
architectural difference is the entire performance story, and the agent must not compromise it.

### Transport

Inertia 2. Not a REST API, not GraphQL. Reasons:

- No token layer to build or secure
- Authorization and tenant scoping stay entirely server-side, where they already work
- Partial reloads (`only: ['records']`) make data-only requests trivial
- Deferred props let widgets stream in independently
- Prefetch on hover makes navigation feel instant

### Stack

| Layer | Choice |
|---|---|
| Backend | Laravel 12, PHP 8.4 |
| Transport | Inertia 2 |
| Frontend | Vue 3 (Composition API, `<script setup>`, TypeScript) |
| Styling | Tailwind CSS 4 with `@theme` tokens |
| Components | shadcn-vue (copied into the package, owned outright) |
| Table engine | TanStack Table v8 + TanStack Virtual |
| Charts | Chart.js or ECharts, lazy loaded, never in the main bundle |
| Build | Vite 6+ |
| Icons | Lucide |

Do not introduce React, Vuetify, MUI, PrimeVue, Element Plus, or any other component library.

### Two portability rules that must never be broken

1. **Nothing in `packages/ui` imports Inertia directly.** Pages receive data as props. A thin
   adapter in the consuming app wires Inertia to those props. This keeps the UI kit usable in any
   context later.
2. **Components never fetch.** They take props and emit events. Only page-level components
   trigger data loads.

## 5. The schema contract

This JSON is the contract between PHP and Vue. Define it first, freeze it, version it. Every
other part of the system is downstream of this.

### Resource schema

```jsonc
{
  "key": "clients",
  "label": "Clients",
  "labelPlural": "Clients",
  "icon": "users",
  "group": "Subscribers",
  "recordKey": "id",
  "routes": {
    "index":  "/app/clients",
    "create": "/app/clients/create",
    "show":   "/app/clients/{id}",
    "edit":   "/app/clients/{id}/edit"
  },
  "permissions": { "viewAny": true, "create": true, "update": true, "delete": false },
  "table": {
    "defaultSort": { "column": "created_at", "direction": "desc" },
    "perPage": 50,
    "perPageOptions": [25, 50, 100, 250],
    "searchable": true,
    "selectable": true,
    "virtualizeAbove": 200,
    "columns": [
      {
        "key": "name",
        "label": "Name",
        "type": "text",
        "sortable": true,
        "searchable": true,
        "copyable": false,
        "align": "left",
        "width": null,
        "visible": true,
        "toggleable": true
      },
      {
        "key": "status",
        "label": "Status",
        "type": "badge",
        "sortable": true,
        "colors": { "active": "success", "expired": "danger", "suspended": "warning" }
      },
      { "key": "plan.name", "label": "Plan", "type": "text", "sortable": false },
      { "key": "expiry_date", "label": "Expires", "type": "datetime", "sortable": true }
    ],
    "filters": [
      { "key": "status", "label": "Status", "type": "select",
        "options": [{ "value": "active", "label": "Active" }], "multiple": false },
      { "key": "created_at", "label": "Created", "type": "dateRange" }
    ],
    "actions": [
      { "key": "edit", "label": "Edit", "icon": "pencil", "type": "link", "permission": "update" },
      { "key": "extend", "label": "Extend expiry", "icon": "clock", "type": "modal",
        "confirm": false, "permission": "update",
        "form": [{ "key": "days", "type": "number", "label": "Days", "required": true }] }
    ],
    "bulkActions": [
      { "key": "suspend", "label": "Suspend selected", "type": "confirm",
        "danger": true, "permission": "update" }
    ]
  }

```

### Data payload

Returned separately, and this is the ONLY thing that moves on filter, sort, or page change.

```jsonc
{
  "records": [ { "id": 1, "name": "...", "status": "active", "plan": { "name": "10Mbps" } } ],
  "meta": { "page": 1, "perPage": 50, "total": 124331, "lastPage": 2487 },
  "cursor": null
}
```

### Rules

- The schema must be **serializable and cacheable**. No closures survive serialization, so any
  closure-based option (dynamic colors, conditional visibility) resolves to a concrete value at
  schema-build time.
- Permission booleans appear in the schema for **UI purposes only**. Every action re-checks
  authorization server-side. The client is never trusted.
- Column keys support dot notation for eager-loaded relations.

## 6. PHP API surface

Model the developer experience on Filament, because that familiarity is the point, but keep the
surface small.

### Panel registration

```php
// app/Providers/PanelServiceProvider.php
Panel::make('admin')
    ->path('app')
    ->guard('tenant_admin')
    ->middleware(['web', InitializeTenancyByDomain::class])
    ->authMiddleware(['auth:tenant_admin'])
    ->brandName(fn () => tenant()?->name ?? 'Admin')
    ->brandLogo(fn () => tenant()?->logo_url)
    ->colors(fn () => tenant()?->theme_colors ?? ['primary' => 'oklch(0.55 0.2 250)'])
    ->discoverResources(in: app_path('Panel/Resources'), for: 'App\\Panel\\Resources')
    ->discoverPages(in: app_path('Panel/Pages'), for: 'App\\Panel\\Pages')
    ->discoverWidgets(in: app_path('Panel/Widgets'), for: 'App\\Panel\\Widgets');
```

Multiple panels must be supported in one application (tenant admin, super admin, customer
portal), each with its own path, guard, middleware, and resource set.

### Resource

```php
namespace App\Panel\Resources;

class ClientResource extends Resource
{
    protected static string $model = Client::class;
    protected static string $icon = 'users';
    protected static ?string $group = 'Subscribers';
    protected static ?int $sort = 10;

    public static function table(Table $table): Table
    {
        return $table
            ->query(fn (Builder $q) => $q->with('plan:id,name'))   // eager load, no N+1
            ->columns([
                TextColumn::make('name')->searchable()->sortable(),
                TextColumn::make('access_code')->copyable(),
                BadgeColumn::make('status')->colors([
                    'success' => 'active', 'danger' => 'expired', 'warning' => 'suspended',
                ]),
                TextColumn::make('plan.name')->label('Plan'),
                DateTimeColumn::make('expiry_date')->sortable(),
            ])
            ->filters([
                SelectFilter::make('status')->options(ClientStatus::class),
                DateRangeFilter::make('created_at'),
            ])
            ->actions([
                EditAction::make(),
                Action::make('extend')
                    ->icon('clock')
                    ->form([NumberField::make('days')->required()->min(1)->max(365)])
                    ->authorize('update')
                    ->handle(fn (Client $r, array $d) => app(LifecycleService::class)->extend($r, $d['days']))
                    ->success('Expiry extended'),
            ])
            ->bulkActions([
                BulkAction::make('suspend')->danger()->requiresConfirmation()
                    ->authorize('update')
                    ->handle(fn (Collection $records) => $records->each->suspend()),
            ])
            ->defaultSort('created_at', 'desc');
    }

    public static function form(Form $form): Form
    {
        return $form->schema([
            Section::make('Identity')->columns(2)->schema([
                TextField::make('name')->required(),
                TextField::make('phone')->required()->rule('phone'),
            ]),
            Section::make('Service')->columns(2)->schema([
                SelectField::make('plan_id')->relationship('plan', 'name')->required(),
                SelectField::make('plan_type')->options(['pppoe', 'hotspot', 'static'])->required(),
                DateField::make('expiry_date'),
            ]),
        ]);
    }
}
```

### Validation: one source of truth

Field rules generate a Laravel validation array server-side. Use **Laravel Precognition** so the
client gets live validation from the same rules without duplicating them in JavaScript. Never
write validation logic twice.

## 7. Artisan generators

The scaffolding experience is a first-class feature, not an afterthought. This is what makes it
feel like Filament.

| Command | Produces |
|---|---|
| `php artisan panel:install` | Publishes config, creates `app/Panel/` tree, registers the provider, adds the Vite entry, installs npm deps |
| `php artisan make:panel {name}` | A new panel (path, guard, middleware scaffold) |
| `php artisan make:panel-resource {Model}` | Resource class with table and form stubs inferred from the model |
| `php artisan make:panel-resource {Model} --generate` | Same, but introspects the database schema and pre-fills columns and fields by column type |
| `php artisan make:panel-page {Name}` | A custom (non-CRUD) page plus its Vue component |
| `php artisan make:panel-widget {Name} --type=stat\|chart\|table` | A dashboard widget plus its Vue component |
| `php artisan make:panel-action {Name}` | A reusable action class |
| `php artisan make:panel-field {Name}` | A custom field type, PHP class plus Vue component |
| `php artisan panel:seed-demo --scale=large` | Seeds realistic multi-tenant demo data |
| `php artisan panel:cache` / `panel:cache-clear` | Builds and clears the schema cache |

`--generate` matters more than it looks. Introspecting the table and mapping column types to
sensible defaults (`boolean` to Toggle, `text` to Textarea, `*_id` to a relationship Select,
`*_at` to DateTime) is what turns a 30-minute task into a 30-second one.

## 8. Vue rendering layer

### Three generic pages render every resource

`ResourceIndex.vue`, `ResourceForm.vue`, `ResourceView.vue`. A new resource requires **zero new
Vue files**. Custom pages get their own component only when the resource is genuinely bespoke.

### DataTable

This one component is roughly 40% of the value of the whole kit. Requirements:

- Server-side sorting, filtering, search, and pagination. Never client-side at scale.
- Column visibility toggling, persisted per user in `localStorage`.
- Row selection with select-all-matching-filter, not just select-all-on-page.
- Virtual scrolling once the row count exceeds the schema's `virtualizeAbove`.
- Sticky header, optional frozen first column.
- Every filter, sort, page, and search term reflected in the URL query string so views are
  shareable and the back button works.
- Loading state that does not unmount the table. Rows dim and update in place; the table must not
  flash or collapse.
- Empty, error, and no-results-for-filter states are distinct and designed.

### Live data and real-time updates

This is a headline feature and the clearest advantage over a Livewire-based panel, so build it
properly rather than bolting polling on at the end.

**The cost model, which is the whole point.** A Livewire-style poll re-renders the component on
the server once per connected viewer per tick, so cost scales with the number of people watching.
A broadcast is emitted once and every connected client receives it, so server cost is constant
regardless of viewers. Never introduce a polling mechanism that re-renders anything server-side.

**Polling is a last resort, off by default.** Any surface for which the backend already emits an
event must use push. Polling is permitted only for cheap aggregates that no event covers, must be
a single lean JSON query rather than a re-render, and must pause when the tab is hidden. A panel
that polls everywhere has reproduced the Livewire problem in a different language.

#### Three tiers, chosen per surface

| Tier | Mechanism | Use for |
|---|---|---|
| 1. Push | Laravel Reverb + Echo, patch one row in place | Anything the backend already emits an event for: session start and stop, usage counters, device online and offline, payment received, provisioning state |
| 2. Poll | Inertia `router.reload({ only: ['stats'] })` on an interval | Aggregates that are not worth an event: KPI counters, chart totals |
| 3. Optimistic | Mutate local state immediately, reconcile with the server response, roll back on failure | The acting user's own writes |

#### The composable

```ts
// useLiveUpdates.ts
const { connected } = useLiveUpdates({
  channel: () => `tenant.${page.props.tenantId}.sessions`,   // private, tenant-scoped
  events: {
    'session.started': (p) => rows.upsert(p.id, p),
    'session.updated': (p) => rows.patch(p.id, { bytesIn: p.bytesIn, bytesOut: p.bytesOut }),
    'session.ended':   (p) => rows.patch(p.id, { status: 'offline', endedAt: p.endedAt }),
  },
  batchMs: 250,          // coalesce bursts into one patch
  pauseWhenHidden: true, // Page Visibility API
  onReconnect: () => reloadData(),  // heal events missed while disconnected
})
```

#### Rules the implementation must follow

These are what separate "smooth" from "janky", and every one of them is a real failure mode:

1. **Patch, never replace.** Mutate the individual row object. Replacing the rows array remounts
   every row, which flickers, drops scroll position, and clears selection.
2. **Key rows by record id**, never by array index.
3. **Do not re-sort or re-filter on a live patch** unless the user asked. A row that jumps out from
   under a cursor mid-read is worse than a slightly stale sort. If a patched row no longer matches
   the active filter, mark it visually rather than removing it, and drop it on the next explicit
   refresh.
4. **Batch and throttle.** Coalesce events inside a 250 ms window and apply one patch. With
   hundreds of concurrent sessions, per-event patching thrashes the renderer.
5. **Animate the change, not the layout.** A short background highlight that fades on the changed
   cell is what actually reads as "live" to a user. Never animate width, height, or position.
6. **Pause when the tab is hidden**, resume with a full refetch. A background tab accumulating
   thousands of buffered events then applying them all at once is a freeze.
7. **Heal on reconnect.** WebSockets drop. On reconnect, refetch the current page of data rather
   than assuming the local state is still correct.
8. **Show connection state.** A small live or reconnecting indicator, so a user never trusts a
   frozen table that silently lost its socket.
9. **Channels must be private and tenant-scoped**, authorized in `routes/channels.php` against the
   panel's guard. A public or tenant-agnostic channel is a cross-tenant data leak that no amount of
   server-side query scoping will catch.
10. **Broadcast lean payloads.** Send only the fields that changed plus the record id. Do not
    broadcast whole models, which risks leaking attributes the recipient is not authorized to see.

#### Backend contract

Events already emitted by the application are reused as-is. An event is only suitable for the
push tier if it carries the record id and the changed fields, and is broadcast on a tenant-scoped
private channel. Where an existing event broadcasts a whole model, add a `broadcastWith()` that
narrows it rather than changing the event's other consumers.

### Theming

All color, radius, spacing, and font tokens live in exactly one file, `theme/tokens.css`, as
Tailwind 4 `@theme` custom properties in `oklch`. Per-tenant branding overrides those custom
properties at runtime through a style block injected from shared props. Never compile a
per-tenant CSS bundle.

```css
@theme {
  --color-primary: oklch(0.55 0.20 250);
  --color-surface: oklch(0.99 0 0);
  --radius-card: 0.75rem;
}
```

## 9. Multi-tenant SaaS requirements

Non-negotiable. The kit must be safe by default, because a panel framework that leaks tenant data
is worse than no framework.

1. **Never query raw.** Resources query through Eloquent models carrying a tenant global scope.
   Raw `DB::table()` is forbidden inside the package, since it bypasses that scope.
2. **Schema cache keys must include the tenant id and a permission fingerprint.** A cache key of
   `panel:schema:clients` will serve one tenant's schema to another and one role's actions to a
   role that lacks them. Use
   `panel:schema:{panelId}:{resource}:{tenantId}:{permissionsHash}:{appVersion}`.
3. **Authorization on both ends.** Schema carries permission booleans so the UI hides what the
   user cannot do. Every controller action independently calls `authorize()`. The client is a
   convenience, never a gate.
4. **Per-tenant branding** through runtime CSS custom properties, from shared props.
5. **Per-tenant feature flags** hide whole resources from navigation and return 404 from their
   routes when disabled.
6. **Panel-level guard isolation.** Each panel declares its own guard. Resolve the user with
   `Auth::guard($panel->guard())`, never a bare `$request->user()`, which silently returns null
   under a non-default guard and fails open in confusing ways.
7. **Tenant-scoped broadcast channels**, authorized in `routes/channels.php`.
8. **A tenancy test suite.** For every resource, a test asserts that tenant A cannot read, update,
   or delete tenant B's records through the index, show, update, delete, bulk, and export paths.
   This suite is part of the definition of done, not optional.

### Runtime independence: Octane-safe, never Octane-required

**The panel must run at full speed on plain PHP-FPM.** Octane is not a dependency, is not assumed,
and must not be needed to hit any budget in section 10. If a performance target is only reachable
with Octane, the design is wrong and the request count is too high.

Why this is affordable here: a Livewire panel needs Octane badly, because it issues a request on
every interaction and pays framework boot each time. This panel issues very few requests, and
prefetching means most navigations hit no server at all. Removing requests beats making each one
cheaper.

Without Octane, reduce boot cost the conventional way, all of which is standard Laravel:

- `opcache.enable=1` with a generous `memory_consumption`
- `opcache.preload` pointed at the framework, which recovers much of Octane's boot saving with
  none of the persistent-state hazards
- `php artisan config:cache`, `route:cache`, `event:cache`
- Deferred and lazily-registered service providers

**Separately**, write the package so that it is *safe* if a consuming application does happen to
run Octane, Swoole, FrankenPHP, or any other long-lived worker. This costs nothing, is simply good
practice, and prevents a silent cross-tenant leak in someone else's deployment. Requirements:

- **No mutable static state that holds request or tenant data.** Resource instances, resolved
  schemas, the active panel, the current tenant, and any memoized query must never live in a
  static property that survives a request. This is the exact failure mode that produces
  "tenant A briefly sees tenant B's data under load", and it does not reproduce on
  `php artisan serve`.
- **Register the panel manager as a scoped binding**, not a singleton, so Octane resets it between
  requests. Anything holding per-request context uses `app()->scoped()`.
- **Resource discovery runs once at boot and is immutable thereafter.** The discovered class list
  is safe to cache statically. Anything derived from it that depends on tenant or user is not.
- **Schema cache keys must include the tenant id and a permission fingerprint** as specified in
  item 2 above. Under Octane an unkeyed in-memory schema cache will serve the first tenant's
  schema to every subsequent tenant hitting that worker.
- **Never call `date_default_timezone_set()` or otherwise mutate global PHP state** from within a
  request. It persists into every later request served by that worker.
- **Provide an Octane flush listener** in the service provider that clears any package-level
  memoization on `RequestReceived`.
- **Add a test that runs the same endpoint twice as two different tenants in one process** and
  asserts the second response contains no data belonging to the first. This is the single most
  valuable test in the suite.

## 10. Performance budget and mandates

If these are not met, the project has failed at its only differentiating goal.

| Metric | Budget |
|---|---|
| Initial JS bundle, gzipped | < 250 KB |
| CSS, gzipped | < 60 KB |
| Route chunk, gzipped | < 60 KB |
| Time to interactive, cold, local | < 1.5 s |
| Navigation between panel pages, warm | < 150 ms |
| Filter or sort change on 500k rows | < 300 ms server, < 50 ms client render |
| Server memory per list request | < 40 MB |
| Queries per list request | Constant. Never proportional to row count |

### Perception thresholds this is designed against

| Latency | Perceived as | Applies to |
|---|---|---|
| < 100 ms | Instant | Any click, filter toggle, sort, row action |
| < 150 ms | Instant | Navigation between panel pages |
| < 300 ms | Fast | Filter or search against the full dataset |
| > 1 s | Broken | Nothing in this panel may ever exceed this |

### Database mandates (the actual bottleneck)

At 500k rows the frontend costs 5 to 20 ms and the database costs everything else. These are
non-negotiable:

- **Never block a list response on `COUNT(*)`.** Filament and most admin panels do, and it is the
  single largest source of slow admin tables. Choose one per resource:
  - keyset pagination with no total at all, exposing "load more" instead of page numbers
  - an approximate total from `pg_class.reltuples` when no filter is applied
  - the exact count as a separate deferred Inertia prop that arrives after the rows
- **Keyset (cursor) pagination is the default** for any table expected to exceed 10,000 rows.
  `OFFSET 100000` forces Postgres to walk 100,000 rows; `WHERE (sort_col, id) < (?, ?)` uses the
  index and makes page 2,000 as fast as page 1.
- **Skip model hydration on lists.** Read-only list queries use `->toBase()` or the query builder
  and return arrays. Hydrating 500 Eloquent models per request is pure waste. Models are for
  writes.
- **Composite indexes matched to real query shapes**, in the column order the query uses, not one
  index per column. Each resource must document the indexes its filter and sort combinations
  require, and a migration must create them.
- **Aggregates are precomputed, never calculated per request.** Dashboard counters are maintained
  event-driven and read from a counter table or cache. No `COUNT` or `SUM` over a large table in
  a request path, ever.
- **`select()` only the columns the schema declares.** Never `SELECT *` on a wide table.
- **One query per list request, plus one per eager-loaded relation.** Enforced by test, below.

### Transport and perceived-speed mandates

- The schema is fetched once per resource per session and cached client-side. Filter changes use
  Inertia partial reloads with `only: ['records']`.
- **Prefetch on intent.** Sidebar links and pagination controls prefetch on hover or focus. This
  is the highest perceived-speed win available: by the time the click lands, the data is in
  memory and navigation is effectively zero.
- **Deferred props for everything below the fold.** The page shell must paint before any widget
  query runs. No widget may block first paint.
- **Optimistic writes.** A row action updates local state immediately and reconciles with the
  server response, rolling back and surfacing an error on failure.
- **Instant local filtering while the server confirms.** Applying a filter narrows the already
  loaded rows client-side in the same frame, then reconciles when the authoritative response
  arrives. The user sees a response in ~10 ms regardless of server latency.
- **Never unmount the table during a reload.** Dim it, keep scroll position and selection, swap
  rows in place.
- **No spinner under 300 ms.** A flash of loading state reads as slower than a brief pause. Use a
  delayed loading indicator.
- **Skeletons must match the final layout exactly** so nothing shifts when data lands. Cumulative
  layout shift target is 0.
- Charts and any heavy dependency are dynamically imported, never in the main bundle.
- Assets are served with Brotli over HTTP/2 or HTTP/3, hashed filenames, and immutable cache
  headers.

### The fixed cost you cannot optimize away

Round-trip network latency between the user and the server is a floor no code can beat. Admins in
East Africa hitting a European region pay 150 to 200 ms per request before any work happens.
Two consequences the agent must respect:

1. Host the application in the region closest to the majority of users. This is worth more than
   every optimization above combined.
2. Design so that the common interactions do not require a round trip at all: prefetch, optimistic
   updates, local filtering, and client-side caching of visited pages.

### Enforcement: budgets fail the build

Performance that is not measured regresses within weeks. Add these as automated tests:

- **Query count guard.** Assert a fixed query count for each resource index endpoint at 10 rows
  and again at 1,000 rows. If the counts differ, an N+1 exists and the test fails.
- **No-count guard.** Assert that the list endpoint's query log contains no unbounded
  `count(*)` against the base table.
- **Bundle size guard.** CI fails if the main chunk exceeds its gzipped budget.
- **Response time guard.** A test seeded with 500k rows asserts the index endpoint responds in
  under 300 ms and the show endpoint in under 100 ms.
- **Lighthouse or equivalent** run against the playground in CI, failing below a set score.

## 11. Build phases with acceptance criteria

Build in this order. Do not skip ahead, and do not abstract before phase 4.

### Phase 0: scaffold (1 day)
Monorepo, playground Laravel app with Inertia and Vue, Tailwind 4, shadcn-vue initialized, both
packages linked by path, demo seeder producing 500k clients across 5 tenants.

*Accept when:* `npm run dev` serves a blank authenticated shell and the seeder finishes in under
5 minutes.

### Phase 1: one hardcoded screen (3 days)
A Clients list. No abstraction, no schema JSON, no resource class. Hardcoded columns, hardcoded
filters, real server-side pagination against 500k rows.

*Accept when:* filter, sort, search, and paginate all work against the full dataset and each
interaction lands under 300 ms server-side.

### Phase 2: a second and third hardcoded screen (3 days)
Routers and Plans. Copy and paste from phase 1. Do not abstract yet. The duplication is the
research.

*Accept when:* three screens work and the repeated parts are obvious in the diff.

### Phase 3: extract DataTable and the query builder (4 days)
Pull the shared Vue table into `packages/ui`, pull filter/sort/search/paginate into a PHP
`QueryBuilder`. The three screens now use them and lose most of their code.

*Accept when:* all three screens still pass their tests and each is under 60 lines.

### Phase 4: the schema layer (5 days)
Introduce `Resource`, `Table`, `Column`, `Filter`, `Action`, the schema JSON contract, the schema
cache, and the three generic Vue pages. Rewrite the three screens as resource classes.

*Accept when:* the three screens are three PHP classes with zero bespoke Vue, and the rendered
result is identical to phase 3.

### Phase 5: forms and actions (5 days)
`Form`, field types, Precognition validation, create and edit pages, modal actions, bulk actions,
confirmations, toasts.

*Accept when:* a full create, edit, and delete cycle works with server-side validation errors
displayed inline, and an action with a modal form runs a service and shows a success toast.

### Phase 6: generators (3 days)
Every `make:panel-*` command, with stubs, plus `--generate` schema introspection.

*Accept when:* `php artisan make:panel-resource Invoice --generate` produces a working screen with
no hand editing.

### Phase 7: SaaS hardening (4 days)
Multi-panel support, per-tenant theming, feature flags, permission integration, the tenancy test
suite from section 9.

*Accept when:* the cross-tenant test suite passes and two panels with different guards coexist.

### Phase 8: widgets, dashboard, live updates (4 days)
Stat cards, chart widgets, deferred loading, Echo-driven row patching.

*Accept when:* a dashboard with six widgets paints its shell in under 400 ms and widgets fill in
independently, and a table row updates live from a broadcast without a refetch.

### Phase 9: packaging (2 days)
Extract to real Composer and npm packages, semver tags, `panel:install` command, a README, and a
quickstart that takes a fresh Laravel app to a working panel in under 10 minutes.

*Accept when:* a brand new Laravel app reaches a working Clients panel using only published
packages and documented commands.

Total: roughly 33 working days for a competent developer with agent assistance.

## 12. What NOT to build

Scope discipline decides whether this ships. Explicitly out of scope for v1:

- Rich text editor, markdown editor, code editor
- Builder and Repeater fields (nested relation editing)
- Wizards and multi-step forms
- Relation managers
- Global search across all resources
- Import wizards
- Soft-delete and trashed filters
- Multi-language UI
- A plugin system

Every one of these is a v2 candidate. Adding any of them to v1 doubles the timeline. If a screen
genuinely needs one, write a custom page for that screen instead of generalizing.

## 13. Installing into a future project

The endgoal. In any new Laravel SaaS:

```bash
composer require panelkit/panel
php artisan panel:install
npm install && npm run build

php artisan make:panel-resource Customer --generate
php artisan make:panel-resource Subscription --generate
```

Then visit `/app`. That flow is the product. If it takes more than 10 minutes on a fresh app, the
packaging is not finished.

Distribution: private Packagist, or a `vcs` repository entry pointing at a private Git remote,
with semver tags. The npm package publishes to a private registry or is consumed from Git.
